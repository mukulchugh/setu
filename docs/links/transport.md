# Setu Links peer transport: operation and wire contract

Status: implemented for issue #15 (ticket 08); same-machine evidence only (see [TEST-BOUNDARIES](TEST-BOUNDARIES.md), U9 and U12 stay open). Vocabulary follows [CONTEXT.md](../../CONTEXT.md). This is the contract other slices (natural-turn delivery, shared-project directory, cross-machine teams) integrate against; it is kept here, in the repository, so it survives scratch cleanup.

Every operation below is a `setu-links/1` engine operation called **only by the trusted Setu service**: never an unauthenticated HTTP or MCP route, never carried on the peer wire, never set from anything a peer says. Unknown fields are refused (`FIELD_UNSUPPORTED`), so a field such as a wake flag cannot ride along.

## What a peer is

A peer is a transport public key (`transport.key`). The connection (QUIC with TLS 1.3, `ring` provider, direct addresses only; no relay, no public address lookup, no port mapping) proves the key. Everything else a peer says about itself is display data. A peer is on the roster only because the trusted service added it (`peer_add`). A message, receipt, hello or published list never creates a peer, a grant, a snapshot or a project.

## The key and the listen address

- The key is created once, whole, owner-only (0600), by writing a private temporary file and publishing it with a hard link, which cannot overwrite: a crash leaves no key or a complete one, and engines racing to create it all read the one winner. An existing key that is empty, short, overlong, group- or world-accessible, executable, a symlink, a directory or owned by another user is refused at once with `TRANSPORT_KEY_INVALID` and a recovery message naming the file; the engine never regenerates or replaces a key by itself. Stale temporary files older than ten minutes are removed, and on a start with a valid key any `transport.key.tmp-*` that is the very same file as the key (a creator died after publishing) is removed too; a refused key and its evidence are never touched.
- `serve` listens on loopback (`127.0.0.1`, a port the system picks) unless the user passes `--listen <address>`. Reaching other machines is a deliberate setting for the cross-machine and packaging tickets, not a default. Peer addresses are stored with `peer_add`; a restart on an ephemeral port changes the address, so a deployment that must survive restarts pins one.

## Wire version 2 and opaque addresses

`Hello` negotiates the single version in `wire::VERSIONS` (now `[2]`). A peer on another version is rejected by name (`PROTOCOL_INCOMPATIBLE`, with the supported versions; `CAPABILITY_MISSING` for missing capabilities) before anything is read or written.

No local path, provider conversation id or provider context crosses the wire or is stored by a peer. A conversation `(provider, native_id, checkout)` is named on the wire by an **address**: `provider` (a plain label), `native_id = "w1:" + SHA-256("setu-links/wire/native/1" 0x00 provider 0x00 native_id)` and `checkout = "w1:" + SHA-256("setu-links/wire/checkout/1" 0x00 checkout)`, plus the managed `session_hint` (a shared directory field). This is a stable pseudonym, not encryption and not authentication: a peer can tell that two addresses are equal, and nothing more is claimed. `Published` and `Deposit` fields that are not shaped like an address are refused (`REQUEST_INVALID`) and nothing is stored.

- A receiver publishes only addresses. The sender stores them in its immutable message row and shows them in `status`/`show`/`peer_list`, so a sender never holds a local tuple of a peer.
- A dialer holds the answer to `Hello` to the listener's standard: a version this engine does not speak, or a missing mandatory capability, marks the link incompatible before anything is published or deposited. Extra optional capabilities are welcome.
- A `send` with `peer_id` must name an address the peer published (`RECIPIENT_ADDRESS_INVALID` otherwise, `RECIPIENT_UNBOUND` for an unpublished one).
- **Matching.** Peer mail is stored with the recipient as it arrived (the address). Wherever a stored recipient is compared with a trusted local conversation, it matches if it is the same local tuple **or** the address computed from that local tuple, through the one function `wire::address` (the SQL functions `setu_wire_native` and `setu_wire_checkout` call it, so there is no second copy and no table of addresses). The sites are: claim selection, read projection (`observed_match`), reconcile hold and release, the resume move, pending counts, acknowledge, redeliver, and the receive-time recheck. The generation fence, snapshot publication and the fenced claim keep comparing local tuples strictly. A mail row whose address the trusted current tuple does not compute can never be claimed; held mail for a replaced conversation becomes queued again when that exact conversation (same native id and checkout) returns or resumes, whether the mail arrived before or after the replacement. A different checkout or conversation never matches.
- **Redelivery.** `status`, `show` and `list` rows carry `observed_match` (true, false, or null when no `observed` was passed): the engine's own answer to "is this message addressed to the conversation I passed". Services ask it instead of comparing tuples. An uncertain handoff is never requeued by anything but an explicit, exact `redeliver`.
- **Retention of earlier data.** Messages already stored by an earlier build keep their local tuple: they are never rewritten or deleted. A pending outbound one is never sent; it ends as `rejected / LEGACY_PRIVATE_ADDRESS`, stays readable, and the user re-sends to the address. The 2-minute cache of a peer's published sessions (`remote_bindings`) is derived data: expired or non-address rows are pruned, and each publish replaces it wholesale.

## Generation = the fence (per managed session)

An integer 0..2^53 owned by the session authority: a persisted per-record counter on the managed session record (same lock as the binding), incremented on every bind, replacement, resume, end, ownership-unknown and checkout-change transition. Not `boundAt`, not wall-clock alone. A heartbeat reuses the current value; an invalidation uses the value its own transition produced.

One row per `session_hint`:
- `binding_publish(p)`: `p < stored` is `BINDING_STALE_GENERATION`. `p == stored`: valid and an identical tuple refreshes; a different tuple is `BINDING_CONFLICT`; an invalid row is `BINDING_FENCED`. `p > stored` replaces the row.
- `binding_invalidate(g)`: `g < stored` is `BINDING_STALE_GENERATION`; otherwise the row becomes invalid at `g` (a bare fence if the session never published) and every publish `<= g` is refused.

### Lifecycle publication and the first mailbox

The managed authority is the sole publisher and invalidator. Both calls pass `existing_store_only`, so the engine never creates a store for them and answers `stored: false` when none exists; the service maps that to "not told" (`LINKS_STORE_ABSENT`) and the announcer retries (a publish on the next turn, an invalidation until it lands). The runtime additionally refuses to start any engine process for either call while the mailbox file `MAILBOX_FILE` (the engine's `DATABASE`; the directory alone proves nothing, it also holds identity and transport state) does not exist. That check is the reason no publication can be stalled outside the engine across the first send: before the file exists nothing is in flight; after it exists a stalled publish is overtaken by a newer invalidation and refused by the persisted generation. The file name is known to JavaScript as metadata only, for one `existsSync`; the boundary test pins the name to the engine's and the single use.

## Operations

`binding_publish {recipient{provider,native_id,checkout,session_hint}, generation, valid_for_ms (1..=300000), project?, resumed_from?: [session_hint, 1..=8]}`: only while the managed record is owned, running, not ended or replaced, and its native binding verified. One transaction: store the snapshot (`valid_until = now + valid_for_ms`), apply the hold/restore decision, and, for `resumed_from`, move mail for exactly this conversation that is located at one of the listed sessions to this session (the immutable message keeps its original hint) and queue it again if it was held for `conversation-replaced` or `session-not-running`; transport, sharing and authorization holds are never released by it. Result `{valid_until, held, released}`, where `released` lists only mail that is still queued when the transaction commits (mail the conversation released but authorization held again is in `held`). Heartbeat at no more than a third of the lifetime passed; a lapsed snapshot is the same as none. `project` is the local project key used by `share_enable`; every publish and heartbeat passes it (absent means unshared). `checkout` is the service's `canonicalCheckout(identity)`; the engine never re-canonicalizes and never sends it to a peer.

`binding_invalidate {session_hint, reason: ended|ownership-unknown|replaced|disabled|checkout-changed, generation}`: fence as above; queued mail for the session is held, matched on the delivery's locator `COALESCE(deliveries.locator, messages.session_hint)`. `binding_show {session_hint}` is passive.

`claim {recipient, expected_generation?}`: `expected_generation` is trusted-internal only. When present it is checked first, before expiry, authorization or any mail is touched: the snapshot must be fresh, valid, exactly `recipient` and at exactly that generation, else `BINDING_NOT_CURRENT` (`details.reason`: `absent | invalid | expired | conversation | generation`) with nothing written, no attempt, and no store created. Absent means the original semantics.

`peer_add {peer_id, label, addresses[]}`, `peer_remove {peer_id}` (drops its grants, holds its waiting mail `peer-revoked`, ends its connection), `peer_list`, `identity`, `transport_status` (passive). `peer_grant` / `peer_grant_remove {peer_id, capability: receive|visible|send, scope}` with scope `{kind:"peer"}`, `{kind:"project", id}` (the sharing policy's current opaque scope `ps_…`, never the local project name) or `{kind:"session", id}`. Removing a grant holds waiting peer mail it no longer covers.

Sharing policy is owned by the directory slice (`share_enable`, `share_disable`, `sharing::standing`); the transport adds no policy operation and no lifetime for it.

## Authorization: three rules, stated where they live

There is no single function; each direction has its own rule, and each reads the store in the transaction that acts.

- **Receive and peer-origin claim** (`authz::admit_receive`, re-run by `authz::gate_all` before every claim and on each maintenance pass): the peer is on the roster; it holds at least one `receive` grant (checked before the session is looked up, so a peer cannot probe which sessions exist); the session has a fresh, valid snapshot; that snapshot carries a project whose sharing policy is `Valid` with `receive`; and a `receive` grant covers the session. Grants only narrow inside a shared project; none opens an unshared project or a session outside every project. `share_disable` deletes the policy, and the next `share_enable` mints a new scope, so grants naming the old scope stop matching.
- **Send** (`outbox::send`): the peer is on the roster, a `send` grant covers the receiver-published entry, and the entry (the receiver's own published view of the session, cached for at most two minutes by the sender's clock) is fresh and exactly the address named. The cache is a filter only; the receiver decides again.
- **Visibility** (`inbound::published_for`): a session is published to a peer only if its snapshot is fresh, its project's policy is `Valid` with `visibility`, and a `visible` grant covers it.

Receive result table: no roster or no receive grant is `PEER_NOT_AUTHORIZED` (nothing stored); a session outside a shared project or without a covering grant is `PEER_NOT_AUTHORIZED`; no fresh snapshot is `RECIPIENT_BINDING_UNKNOWN` (retryable); a fresh snapshot whose own address equals the one sent is stored `queued`; a different address is stored `held / conversation-replaced`. A lapse of any evidence holds waiting mail (`peer-revoked`, `authorization-lapsed`, or #11's `policy-disabled`); mail held only for lapsed authorization follows a new explicit grant; mail held for a revoked peer never returns. A read never shows a held message as queued unless the conversation itself explains the hold.

## Limits, all on the receiving side whatever the sender claims

Body: `mailbox::MAX_BODY_BYTES`, checked before anything is stored (`BODY_TOO_LARGE`); the natural-turn body cap and frame helper are taken from `mailbox`/`frame` as they land and nothing is truncated. Frame: 128 KiB (a transport bound). Deposits: 60 per minute per peer (deferred, `busy`), 200 waiting per peer, 100 waiting per conversation; expiry is the receiver's own seven days and no expiry field exists on the wire. Cancels for messages that never arrived (tombstones): ids are plain bounded tokens, at most 60 recorded per minute and 200 held per peer, only for a peer holding a `receive` grant, kept for eight days (longer than any sender retry) then forgotten; a full cap answers `TOMBSTONE_LIMIT` (retryable), never a cancel that was not recorded. A peer's replies are held to the same vocabulary in one place (`Reply::checked`): an unknown state, an over-long or non-printable reason, a bad sequence or code is replaced by `PEER_REPLY_INVALID`, nothing is stored, and the sender's message stays readable with `transport.last_error` and is retried.

## Cancel

Before any attempt, the sender cancels locally and atomically. After one, `cancel` is `requested` with the best-known state until the receiver confirms it got there first; a claim that won the race is reported as `refused` with the true state. Only a confirmation makes the message `cancelled`.

A cancel answer must agree with itself: `cancelled` is valid only with state `cancelled`, and `refused` only with a state other than `cancelled`. A contradictory answer is `PEER_REPLY_INVALID`: nothing is stored and the cancel stays `requested`.

Two different things can make a sent message read `cancelled`, and they are kept apart. The **sender's cancel** (`transport.cancel` is `requested`, then `confirmed`) is confirmed only by an answer to the sender's own cancel request. The **recipient's own cancellation** (the receiving user cancelled the message in their inbox, which the receiver's engine allows while it is queued or held) is the recipient's state to report: it arrives as a receipt, the sender shows `state: cancelled` with `transport.remote_state: cancelled`, and `transport.cancel` stays `none`. The sender never invents a cancel confirmation for it. A recipient may legitimately report any delivery state at any time (fast handoff and acknowledgement, expiry, repeats), so a `Deposited` answer is not restricted beyond the vocabulary.

## Lifecycle owner

`setu-links serve --data-dir <dir> [--listen <address>]` is one process per directory (an exclusive lock; a second start prints `already-running`). `links-transport.js` (`start`, `status`, `stop`) is the owner interface; service packaging wraps it later. `start` reports a daemon ready only with the same proof `stop` uses (live process, started no later than the daemon recorded, exact command line), so a status file left by a dead daemon is never taken for the one that is starting. `stop` signals only when the engine says the lock is held, the live process began no later than the daemon recorded, and its command line is exactly `<engine> serve --data-dir <dir>` with at most one `--listen <address>`; a start the engine refuses is reported with the engine's own reason.

## Schema and merge notes

The transport migration is 2 to 3 on top of the directory slice's 1 to 2 (`messages.project`, `sharing_policies`, `presence`) and the natural-turn `deliveries.locator`; `src/sharing.rs` and that step in `store.rs` are carried provisionally and replaced by the reviewed slices at integration. Shared hunks: `mailbox.rs` (send route and digest, status/show outbox fallback guarded by schema version, cancel, claim fence/peer gate/attribution, wire-aware matching, `sweep`/`maintain`), `store.rs` (registers the address functions on every connection), `args.rs`, `protocol.rs`, `util.rs`, `lib.rs`. `binding::move_and_release` stands in for the natural-turn `resume` and must keep that slice's history behavior for handed-off and unknown rows when substituted.
