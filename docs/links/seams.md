# Setu Links: existing code seams

Researched against `f6dda1a384bd03566e5e88f2ca898a6ce3a3976d` (Setu 0.3.0 main). Module names are pinned to that commit and may drift; re-check before relying on a line of this file. Nothing here has been implemented.

## What exists and what Links should do with it

| Seam (module role) | What it does today | Links recommendation |
| --- | --- | --- |
| Managed agent services (`managed-agent-services.js`) | Composes sessions, trusted hook ingress, terminal adapter, attention, handoff and headless runs. Writes a per-session Claude settings JSON and a Bun hook program, launched with `claude --settings`. Registered hook events: `Notification`, `PermissionRequest`, `SessionStart`, `Stop`. | Add one more registered event (`UserPromptSubmit`) and a response path. Extend `receiveHook`; do not add a second hook channel. |
| Hook program (generated inside the same module) | Reads hook JSON on stdin, POSTs `{provider, launchToken, payload}` to `/api/attention/hook` with a 1 s timeout, ignores every failure, writes nothing to stdout. | A prompt-submit variant must read the portal response and write the provider's context output, then report that it wrote it. It must never block the turn and must finish quickly. Failures before the engine claim leave mail queued; at or after the claim they are `handoff-unknown` (see the spec's handoff protocol). Do not promise that a failed hook wrote nothing. |
| Trusted hook ingress (`terminal-attention.js`) | `registerLaunch` maps launch token to managed session. `SessionStart` calls `bind`, which maps `provider:nativeSessionId` to the managed session and **deletes the launch token**. `resolveHookSession` resolves later events by native id plus `cwd` alone, with no secret proof. | **Gap found:** both maps are in memory. After a portal restart every native binding is gone, so attention hooks silently stop resolving until relaunch. Exact Links delivery cannot rely on this. Native ID plus cwd is only a locator. Persist the binding on the session record, retain the launch capability for the session's life, store only its digest, and require it for all production hook resolution, attention included (ticket 01). |
| Agent session records (`agent-sessions.js`) | Durable records in workspace state (`agentSessions`): id, repo, name, checkout path and identity, tool, pid/process start, state, ownership, Ghostty terminal id. No provider-native conversation field. Reconciles against process evidence. | This is the authority for local process, checkout identity and (new) native conversation binding. Add the binding here, not in a Links table. |
| Checkout identity (`checkout-identity.js`) | Filesystem incarnation fingerprint of a linked worktree, excluding HEAD. | Use it as the recipient's checkout proof. A message must not follow a replaced checkout. |
| Terminal attention (`terminal-attention.js`) | Provider hook events become attention items with kinds permission, question, between-turns. A `Stop` event is the only existing idle signal. | Use `between-turns` as an observation only, never as proof the agent can accept a wake. Remote attention needs its own authenticated path (ticket 06); do not forge a provider hook. |
| Terminal adapter and review handoff (`native-terminal.js`, `review-handoff.js`) | Ghostty AppleScript adapter. `deliver` types text into an existing, verified, exactly identified terminal session and refuses to launch one. | Only candidate for Send now on Ghostty-launched managed sessions. Its effect on an idle Claude prompt is unproven; ticket 06 starts with a probe. |
| Spans terminal transport (`spans-cmux.js`) | Adapter-injected; never invokes cmux. | Not a prerequisite for Links. Do not present as an integration. |
| Route plumbing | Three places must agree: the public route table (`portal-routes.js`), the dispatch tables (`portal-resource-services.js`) and the service object composed in `portal.js`. `portal-wiring.js` is an older prototype and owns no runtime route. | Add `/api/links/*` through all three. Add route parity tests. |
| CLI (`cli.js`, `cli-api.js`) | Subcommands registered in a table, call the portal through `cliApi` with `x-setu-source: cli`; refuse rather than launch when the portal is down. `cmdSessions` is the closest pattern. | `setu links ...` follows it. Same PORTAL_REQUIRED convention. |
| MCP (`mcp-server.js`, `claude-plugin/.mcp.json`) | Generic HTTP MCP at `localhost:2999/mcp`, no per-caller identity. | Cannot identify the calling session. Agent tools need a session-bound entrypoint (ticket 05). |
| Workspace state (`workspace-state.js`) | Validated JSON stores with locks. | Not a message store. Keep message state out of it. |
| Spans archive (`spans-store.js`, `spans-model-store.js`) | Private SQLite via `bun:sqlite`, default root `~/.local/share/setu/spans`. Atomic view-plus-events commits with unique event IDs. | Receives redacted projections of message outcomes (ticket 07). It never owns delivery state. |
| Package scripts (`package.json`) | `test` is an explicit list of test files; `files` is an explicit allowlist of shipped modules. | Every new test file must be added to `test`, and every new shipped module or artifact to `files`, or CI will not run or ship it. |
| Toolchain | `bun` for JS. Rust 1.99.1 is verified installed in an isolated build-tools directory with no shell PATH change, so `cargo` is not on the default PATH and builds invoke the isolated toolchain explicitly. No `engines/` directory exists yet. | Reproducible CI provisioning is an acceptance item of ticket 02. |

## Recommended pragmatic boundaries

1. **One authoritative delivery store: the Setu-owned Links engine.** It alone opens its database. JavaScript is a client of an operation protocol and never reads or writes message state directly. There is no JS mailbox beside it, now or as an interim step.
2. **Local first, transport later, same store.** The first local mode may be one process per operation (JSON in, JSON out) over the reused store; confirm against what the reused store supports. A long-running mode that adds peer transport reuses the same operation protocol and the same store. Local delivery ownership never moves to the transport.
3. **Identity stays with Setu sessions.** Session services own process, checkout and native-conversation binding. The engine stores the recipient locator it was given at send time and enforces matches at claim time; it does not discover or infer identity.
4. **Delivery goes through the portal.** The hook posts to the portal, which verifies the binding against the session record and then calls the engine. If the portal is down before the claim, mail stays queued. After the claim, any uncertain result is `handoff-unknown` and is never resent automatically.
5. **Selected reviewed store and transport source is reused, pinned to a recorded revision and checksum.** Reuse is already authorized and is not a gate. Ticket 02 brings in the store; ticket 08 the transport. Licenses and provenance are kept in separate legal metadata. There is still exactly one mailbox store.
